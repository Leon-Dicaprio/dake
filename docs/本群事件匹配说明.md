# 本群事件匹配说明

2026-11-17 用户确认：本模块处理“新消息 → 本群事件”；跨群的“事件 → 事件”关联由另一功能处理。本文件覆盖旧方案中本模块直接跨群认回的约定。

## 实际处理顺序

1. 官方消息继续按 ID 与内容版本去重，空批及仅有已确认机器人消息时不调用模型。缺少稳定群 ID 的消息记录待确认，正常完成窗口，不猜群名。
2. 按客户 UID、来源、稳定群 ID 隔离消息和普通聊天上下文。同一窗口各群顺序处理；同群新增按 `GROUP_BATCH_CHARS` 分批，不截断或丢弃新增消息。模型在事务外调用，各批结果暂存后统一在原窗口事务提交，后批失败则整窗不写入。
3. `event_group_links` 以原事件证据关联群，先通过群索引限定查询，再按原有近期／更早分页预算检索。显式事件 ID 和完整消息引用都有独立有界查询，不受普通扫描名额挤占。关键词用于排序；同群预算内的非词法命中也作为语义候选，避免短指代漏掉旧事项。请求号、订单号只作为词法线索。
4. 每批最多提供原配置的 8 个候选及有限原文背景。旧跨群事件只补取当前群的证据，历史事件及原收据不拆分、不改写。较早／已关闭事件仍可检索；客户确认恢复和复发沿用已有证据规则。
5. 模型在一次正常调用中完成事项拆分、对象、事实及归属提取。沿用主分支合约 `4.0` 的多标签、`typed_attributes`、状态及优先级提案；历史 `matching` 对象字段只供核对，缺失不猜测。分类标签变化不改变事项身份，明确认回后继续更新原 `event_id`。没有增加“先分类再匹配”的第二轮调用，已有一次结构纠正上限不变。
6. 程序检查本群范围、明确引用、对象冲突和实际新旧依据，再通过原归属服务写入。事件、群索引、消息处理标记、执行收据在同一 MySQL 事务提交。

## 决定规则

| 条件 | 结果 |
| --- | --- |
| 更新目标为本批同群候选，新旧引文有效，对象无明确冲突，恢复边界允许 | 更新原 `event_id` |
| 引用定位失败、指向多个事件或与更新目标冲突 | 待确认 |
| 新建建议的当前原文依据包含明确旧事件引用 | 待确认；文本引用也可能是对照或否定，不能强改为更新 |
| 新旧事项对象字段不一致 | 待确认；缺少字段不算冲突，别名差异也需核对 |
| 模型建议独立新事项，事实有效、无未决旧候选、检索完整 | 程序生成新 `event_id` |
| 首次接入、本群没有可关联事件，但当前问题和跟进事实明确 | 可首次建档；新建不等于问题刚刚发生，不补写未提供的历史 |
| 索引未知／缺失、扫描或候选截断、快照不安全等导致检索不完整 | 新建建议降为待确认，零命中不证明应该新建 |
| 旧事项没有新增事实 | 非业务／无需推进，不修改事件 |
| 新建建议同时要求更正／替换旧摘要，但直接引文有效 | 该事项降为待确认，保留原模型建议，其他合法事项继续提交 |
| 恢复／复发边界与归属动作矛盾，但直接证据有效 | 只将冲突事项降为待确认，不修改其旧事件，其他合法事项继续提交 |

动作冲突先核验全部直接事实和字段引文；伪造引文、非法消息引用、畸形结构仍按合约错误处理，不能借待确认绕过来源检查。该规则计入本群策略版本；跨版本的新任务不关联为旧策略重试，旧执行记录和失败原因继续保留。

恢复动作冲突同样先校验连续性引文，再做非写入降级；结构或证据错误仍中止窗口。原建议保留在过程记录中，程序决定明确标记待确认，不擅自把不确定的恢复解释为已恢复或复发。

非业务筛选结果保存为审计字段 `business_classification=non_business`、`processing_action=no_action`。内部 `duplicate` 暂时保留以兼容旧合约、原收据和变化查询；不新增事件或修订。原文和判断依据仍可追溯。无事实变化的更新也不产生空修订。

2026-11-17 验收修正：关键词截断与候选不完整分开记录。空事件库不会因长消息超过关键词预算而无法首次建档；本群模式将扫描内的语义候选纳入排序，不再以关键词零命中直接排除，所以单独的 `clues_limited` 不代表候选缺失。明确引用被截断、扫描未完成、候选／证据预算不足、索引不明或版本不安全仍会使 `incomplete=true`，保留原有待确认保护。首次记录时“昨天也有”不单独构成待确认理由；真实指代不清、对象冲突和恢复边界问题仍需核对。

官方消息目前没有已确认的权威事项编号或结构化回复关系，不能把自然语言中的工单号、订单号或请求号冒充唯一事项绑定。获得正式接口后，再扩展精确路由；本轮不声称自由文本已能脱离模型自动归属。

## 迁移与历史记录

所有新任务统一按本群处理，不再提供灰度开关或跨群旧策略。群索引为运行前提；先停止本项目写入服务，执行：

```bash
docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" exec mysql --user="$MYSQL_USER" "$MYSQL_DATABASE"' < backend/migrations/006_event_group_links.sql
```

迁移完成后用新代码重启服务。迁移只增加及回填索引，不重洗消息或改写历史事件。旧证据没有群 ID 时，只使用与证据 digest 相同的消息补群；无法还原的保留未知，不能用编辑后的当前消息补造历史归属。未知索引会让新建进入待确认，需要核对历史数据。

所有事件写入在原事务中维护群索引，缺表会失败回滚。新任务冻结分批预算和规则版本；旧任务及旧调度模板缺少当前版本或版本不同时拒绝执行／恢复，不自动转换或重洗。历史事件、运行记录和收据继续可读。旧策略下未完成的提交核实或展示恢复须先在原版本处理，再显式迁移调度策略；重复开始不会重置进度。

本群窗口快照标记 `snapshot_scope=related_events`，只含本轮加载或改动的相关事件，`event_count` 单独统计客户总数。完整历史保留在事件修订中。候选及展示恢复按事件 ID 加载，不复制全客户事件正文。历史全量快照保持原语义。

## 验证与限制

离线用例在 `backend/tests/test_group_matching.py`。真实 MySQL 合成用例在 `backend/tests/test_group_matching_mysql.py`，通过 `scripts/verify_execution_mysql.py --suite matching` 或 `--suite all` 执行；连接参数必须显式指定独立临时实例，禁止使用 3307 业务库。

覆盖同群更新、跨群隔离、引用及对象冲突、检索不完整、无新增事实、分批不漏消息、事务回滚、旧数据回填和原收据恢复。没有进行真实聊天质量或吞吐评测。

本轮约束候选及单次输入体积，未增加全局模型配额；按群和字符分批可能增加调用次数，不能宣称总费用已经下降。字符预算不等于精确 token 预算。同窗口保持原子提交，后批失败时未提交前批可能在重试中再次调用模型。后续容量验收需统计请求数、输入／输出用量、排队延迟及误建／误合并率，再完善全局配额与调度等待。

XHub 建连等待至多 5 秒，模型生成等待使用任务冻结值；网络错误统一交给调度层有限重试，不叠加连接层重试。HTTPX 沿用原有代理路由和证书校验。
