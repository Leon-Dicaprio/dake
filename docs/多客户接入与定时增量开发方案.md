# 多客户接入与定时增量开发方案

日期：2026-11-16。状态：开发规划，接口待提供，尚未实现自动运行。

本方案整理已确认的线上接入流程：通过后续提供的全量群聊接口发现客户；群缺少客户 UID 时，通过关键词搜索相关群补查；确认 UID 后筛选大客户、获取主备负责人，再由定时器驱动现有增量服务持续处理。找不到 UID 或归属不明确的群暂不分析，保留待确认记录。

本轮目标为本周三（2026-11-18）的线上验收准备多客户运行能力。验收 UID 范围、部署环境、可接受延迟及接口协议仍待对接；不将预计提供的接口写成已可用能力。

## 已确认的接入来源

群发现使用后续正式提供的全量群聊接口，不接入此前探查的 Mars 内部群列表接口，也不使用旧开发数据库。新接口的服务归属、地址、方法与鉴权以接口负责人提供的文档为准。

现有消息取数仍使用官方 `POST https://ts.qiniu.io/api/mars_alert/qq/chatRecords`，参数为客户 UID 和含首尾的日期。分钟级新接口到位后增加来源适配，继续复用统一消息、增量分析与事件更新服务。

| 接口能力 | 用途 | 对接重点 |
| --- | --- | --- |
| 获取所有群聊 | 发现群及其客户关联 | 稳定群 ID、群名、客户 UID、分页完整性、覆盖范围 |
| 按关键词搜索相关群 | 缺失 UID 时查找相关群和客户线索 | 查询范围、匹配方式、分页、返回的 UID 含义 |
| 按客户 UID 查询 level | 判断是否属于本期大客户范围 | 等级枚举、大客户判定口径、未知与不存在的区分 |
| 按客户 UID 查询主备负责人 | 维护客户责任归属 | 主备人员稳定 ID、姓名、缺失与多值情况 |
| 按 UID 和分钟级起止时间获取聊天 | 持续获取待处理消息 | 必须确认返回消息正文而非仅群信息，以及时间边界、分页、迟到与修订规则 |

增量游标、消息变更类型、批量按消息 ID 查询、批量客户资料查询是建议支持的能力，目前未确认提供。消息游标若可用，应能覆盖服务端迟到入库和后续修订；事件业务时间仍使用 `send_time`。

## 客户发现和 UID 补查

处理顺序如下：

1. 分页获取完整群清单，保留接口来源、群 ID 和同步时间。
2. 已明确命中供应商或内部产品群排除规则的群可提前跳过 UID 搜索。
3. 接口直接返回明确客户 UID 的，校验后保存映射。
4. 缺少 UID 的，从群名称等信息中提取有限关键词，通过官方相关群搜索接口补查。
5. 检查候选群与原群是否属于同一客户，形成确认映射或待确认结果。
6. 对已确认客户 UID 去重，查询客户等级，筛出允许处理的大客户。
7. 获取主备负责人并加入启用客户清单，供定时执行读取。

账号 UID、群 ID、客户 UID 必须分别识别。不得从群名数字直接生成客户 UID，也不得将关键词搜索的第一条结果直接绑定为客户。

即使搜索结果只有一个 UID，也要有足够关联依据。接口提供的正式群客户映射可以作为依据；仅名称相似时先保留候选，交由人工确认。多个候选 UID、无命中、分页不完整和接口失败要分别记录，不能全部当成“无客户”。一期不通过递归扩展搜索无限扩大范围。

未找到或无法确认 UID 的群不进入事件分析，不分配虚构 UID，不判为非大客户。保存群 ID、候选客户、查找依据、最后尝试时间和原因；支持有限重试及人工补充。查询失败不能覆盖已有已确认映射。

映射后续发生变化时保留历史，暂停冲突映射的自动使用，不将旧消息直接搬到另一客户。现有消息存储拒绝同一消息 ID 跨客户覆盖，该约束继续保留。

## 群过滤与客户筛选

群用途规则沿用 [群识别与消息过滤开发方案](群识别与消息过滤开发方案.md)：普通内部协作群与客户群保留，供应商名称规则和明确排除清单优先。当前样例三个群全部保留。

群过滤与客户准入是两道独立判断。未知群用途默认保留，仅表示不因群用途排除；如果客户 UID 尚未确认或大客户身份未知，仍不能进入自动事件处理。

UID 尚未确定时，只能使用明确适用于该来源的全局排除清单或已确认名称规则，不能套用另一个客户的规则。原群过滤方案的按 UID 配置继续用于已确认客户；若增加全局配置范围，需显式定义，不能通过缺省 UID 隐式扩大规则作用域。

大客户判定规则由官方等级说明确定，不自行发明 level 阈值。查询结果明确为非大客户时不纳入本期运行；首次等级查询失败或结果未知时待确认。已有客户的资料临时刷新失败时保留最后成功结果，标记过期并按明确的有效期策略使用，不能静默移除或无限期沿用。

主备负责人是客户责任信息，与事件实际跟进人分别保存。不能因为某人是客户主负责人，就断言其已经参与事件处理。负责人暂时缺失时标记未知，不编造，也不应单独阻断已确认客户的事件提取。

## 两类定时任务

采用外部定时器触发轻量执行入口，复用现有业务服务。第一阶段保持单实例和有限并发，不引入分布式任务平台，不在定时脚本中复制归属、分类或回放逻辑。

| 任务 | 工作内容 | 运行策略 |
| --- | --- | --- |
| 客户范围同步 | 获取群列表、补查 UID、更新等级和主备负责人 | 独立可配置频率，支持手动同步；不随每个消息窗口重复查询全部资料 |
| 消息增量处理 | 为启用客户补跑待完成窗口，生成或更新事件 | 处理周期缺省沿用 `15m`，定时触发频率与业务窗口大小分别配置 |

每次增量执行应做到：

- 读取启用 UID 清单，每个 UID 和分析版本分别维护进度。
- 使用 `Asia/Shanghai` 计算动态处理上界，优先处理完整窗口，可配置数据延迟缓冲；不继续使用演示的固定结束日期。
- 从已保存进度继续，按顺序补跑，限制单次最大窗口数和运行时间，避免某客户积压占满整轮执行。
- 一个客户失败不阻断其他客户；记录失败窗口，不跳过后续无法安全处理的业务顺序。
- 同客户不重叠执行，沿用客户锁及消息幂等；定时器重复触发时不重复领取相同任务。
- 重启后根据数据库处理状态与执行记录恢复。水位文件仅辅助选窗，丢失不能导致重复事件。
- 网络暂时失败可有界重试；事务提交结果不明必须先核实，不能盲目重跑。已提交但展示失败按原收据恢复。
- 定时任务接入 `processing_runs` 和既有执行记录，页面能看到处理范围、进度、失败与最近成功时间。

现有 `process` 每次仅执行一个窗口，`replay` 处理有限范围。新定时入口负责动态窗口和有界补跑，调用同一增量服务；首次运行起点按客户明确配置，不从最早历史自动全量分析。

## 取数和本地写入

分钟级接口支持后，按当前窗口及补漏范围取数，逐页确认完整性再推进进度。只有发送时间过滤仍可能漏掉迟到消息，应保留重叠回溯；有正式变更游标时优先按其协议获取变化。未提供消息删除或修订能力时，明确记录边界，不假装已覆盖。

来源适配器统一消息后，继续按来源和消息 ID 幂等写入 MySQL：新消息新增、相同版本跳过、修订消息更新并进入相应待处理流程。补取历史不能把未来窗口消息提前交给抽取器。

原始响应、真实群映射及客户资料仅放本地私有存储，不写入文档、测试或普通日志。日期接口沿用现有按日缓存；新接口的分页响应缓存格式在协议确认后设计，不能让不同页或不同窗口相互覆盖。初期不删除既有消息或历史事件。

事件更新、证据关联及消息已处理标记保持原子提交。取数频率和业务分析频率可以分开，但不能形成两套重复的处理逻辑。

## 查询性能与存储职责

本地 MySQL 继续作为业务存储。先利用客户、时间、ID 的结构化字段和索引定位，再按需加载正文，避免把所有数据放进单块 JSON 后反复扫描。

- 群客户映射、客户等级和主备负责人需要可持久化、可查询的记录；正式表结构在接口字段明确后确定。重复同步按稳定 ID 更新，不追加无界重复数据。
- 消息写入采用有界批量比对与写入，减少逐条查询往返。待处理消息的状态应可索引，避免每轮从项目起点扫描处理标记 JSON。
- 历史检索先读取少量事件标题、摘要、对象和时间，再读取候选关联聊天；会议提出的 30 天范围应作为可配置参数对接，不在此文改写当前运行配置。
- 明确保存事件与消息、执行、修订的关联。变化面板按关联和分页读取，不再现场扫描所有模型阶段和任务周期 JSON。
- 完整模型输入输出保留为审计详情，展开时按需读取，不进入默认列表响应。

这些属于后续存储优化设计，实施时提供迁移和旧数据兼容方案，不能绕过提交收据或证据版本校验。是否增加语义检索由候选召回测试决定，不将向量数据库作为接入前置条件。

## 接口到位前后如何推进

接口到位前，可以实现合成数据驱动的来源适配边界、UID 补查状态、群规则和轻量定时编排，并优化现有变化查询。归属更新、分类标签由已分配的任务推进，共用输入输出合约。

接口到位后，先小范围只读验证群与 UID 覆盖、分页和时间边界，再接入客户筛选，最后启用指定客户的真实定时处理。新增客户的线上取数及模型处理范围须明确，原样例客户的 XHub 授权不自动扩展到所有发现的 UID。

上线前还需确认部署机器、网络与鉴权配置、处理客户清单、首次起点、运行周期、追赶上限及验收延迟。令牌和密钥通过本地私有配置提供，不放在命令行、文档或提交说明中。

## 验收场景

测试使用合成群、客户和消息；正式联调结果只记录计数、状态与耗时。

| 场景 | 预期结果 |
| --- | --- |
| 多群直接返回同一客户 UID | 维护多群映射，客户资料和增量任务按 UID 去重 |
| 原群无 UID，相关群有可靠客户关联 | 保存依据，确认后进入等级筛选 |
| 仅名称相似或存在多个候选 UID | 待确认，不自动绑定 |
| 无搜索结果或搜索接口失败 | 区分原因，暂不分析，支持重试 |
| 未知群用途且没有 UID | 不因默认保留而进入事件分析 |
| 命中明确排除规则 | 跳过分析，可提前省略 UID 搜索 |
| 等级未知、首次查询失败或明确非大客户 | 分别记录，不能混为同一状态 |
| 全量群同步只有部分页成功 | 标记不完整，不据此停用未返回的客户或群 |
| 多客户持续执行，其中一个失败 | 其他客户继续，失败窗口和进度可查询 |
| 定时器重复触发或停机后补跑 | 不重叠领取、不重复建事件，按窗口有界追赶 |
| 迟到、修订及时间边界消息 | 按接口能力补漏，幂等处理，不提前使用未来消息 |
| 负责人缺失或资料刷新失败 | 未知／过期明确，不编造、不覆盖有效资料 |
| 群 UID 映射冲突或变更 | 留痕并停止冲突绑定，不跨客户覆盖历史消息 |

交付为接口适配、群客户映射与待确认记录、客户筛选、定时执行入口、运行可观测性和回归验证。本文不代表接口已可调用、群过滤已上线或定时器已部署。
