# 定时增量验收与名单交接

2026-11-17。实现范围为客户名单接入、起始日期配置、持续窗口编排、客户轮转、持久进度、有限重试和暂停恢复。正式消息源仍为 `chatRecords`，客户发现和筛选由其他模块实现。

## 验收前准备

1. 按 README 启动本地 MySQL，完成 `001`、`002`、`003`、`004` 迁移。
2. 上游提供 `data/config/scheduled_customers.json` 完整快照，字段、启停与更新约定见下节。不得用测试客户替代真实名单；测试只运行在专用隔离库。
3. `.env` 的 `SCHEDULE_ENABLED=1` 启用 API 进程中的触发器，保持一个 Uvicorn worker。也可独立运行 `dake schedule run`；外部定时器仅调用 `schedule tick` 时，必须保留一个队列执行器。
4. 用 `dake schedule start --start YYYY-MM-DD` 或 `POST /api/v1/schedules/start` 配置最初日期。只有起始日，没有固定结束日；同一配置重复启动不重置进度。

正式客户名单未交接时，核心功能可独立使用合成来源完成验收，但不能宣称已完成客户名单真实联调或多客户真实模型质量验收。

## 名单交接与运行配置

当前适配器从根目录 `data/config/scheduled_customers.json` 读取完整快照，真实 UID 只留在私有存储。以下示例全部虚构，不要导入业务库：

```json
{
  "schema_version": 1,
  "complete": true,
  "customers": [
    {"uid": "synthetic-customer-a", "enabled": true},
    {"uid": "synthetic-customer-b", "enabled": false}
  ]
}
```

上游负责确认客户归属、等级和有效授权，并原子替换快照；`CustomerSource.load()` 成功返回表示名单完整，失败必须抛异常，不得伪造空名单。正式接口到位后替换 `services/scheduled_customers.py` 的适配器，调度规则不变。明确完整的空名单会停用全部客户；缺少、损坏或不完整名单时，原进度保留，本轮不新增任务。名单指纹未变时不反复批量更新；重新启用客户不会解除其错误或人工暂停。

```bash
.venv/bin/dake schedule start --start 2026-11-08
.venv/bin/dake schedule status
.venv/bin/dake schedule run
.venv/bin/dake schedule pause --id <schedule_id>
.venv/bin/dake schedule resume --id <schedule_id>
```

默认检查间隔为 5 秒（`SCHEDULE_POLL_SECONDS`），业务窗口固定为已确认的 15 分钟；补跑期间无需每窗口等 15 分钟。单次触发最多处理 128 条可执行状态，沿用队列最多 32 个未结束任务；满后保留顺序，下次继续，不截断积压。重复启动不会重置原始日期、冻结策略或进度；变更原配置会拒绝覆盖。

临时错误的三个重试间隔默认是 60／300／900 秒，可通过 `SCHEDULE_RETRY_DELAYS_SECONDS` 配置三个 1 至 86400 秒的整数。调度执行关闭取数客户端内层重试，避免次数相乘。协议、鉴权或最终模型校验错误直接暂停。暂停不撤销已排队或正在执行的最多一个窗口；显式恢复重新给予重试预算，提交不明须先核实。业务 `review` 属于成功处理，不无限重试。

`INGEST_LOOKBACK` 默认 2 天，补查仍在线刷新官方日期接口。原始起点与当前窗口起点分开，时间范围之外的迟到或修改不保证自动发现。恢复展示只读取原收据和精确修订，不重新取数或调用模型；原版本缺失即停止，不用新版本替补。入队与状态绑定同事务，业务进度按真实提交收据对账，文件水位丢失不会导致重建事件。仍沿用单实例执行，不提供分布式隔离保证。

## 现场检查

| 场景 | 检查结果 |
| --- | --- |
| 两个客户都有积压 | 每客户每任务一个窗口，交替获得处理机会 |
| 一个客户没有任何消息 | 原始起点保留，完整空窗口的 next_start 持续推进，无模型调用 |
| 最新 15 分钟窗口尚未结束 | 不提前处理，不额外添加 5 分钟延迟 |
| 取数稍后才返回较早消息 | 补漏回查发现，按原 send_time 处理，不因任务起点前移而排除 |
| 重复触发、队列已满或同客户手动任务在运行 | 不重复提交，未入队客户保留顺序，下次继续 |
| 完整名单未变化 | 不反复批量改写客户状态 |
| 名单失败或不完整 | 原进度保留，不误停用全部客户，本轮不新增任务 |
| 窗口临时网络错误 | 1／5／15 分钟最多三次重试；其他客户继续 |
| 超过重试上限或配置错误 | 持久暂停该客户，重启仍保持 |
| 客户恢复 | 从失败窗口继续，原任务记录与原始起点保留 |
| 数据库提交确认丢失 | 标记提交待核实，不自行重复分析；显式核实后才恢复 |
| 事件已提交、进度展示失败 | 从原收据恢复，不再次调用模型、不重复写事件 |
| 服务停止后重启、文件水位删除 | 读取数据库关联任务与连续进度，空窗口也能恢复 |

## 自动验证

常规后端与前端：

```bash
.venv/bin/python -m pytest -q backend/tests -m 'not mysql and not isolated_mysql'
RUN_MYSQL_TESTS=1 .venv/bin/python -m pytest -q backend/tests -m mysql
npm --prefix web run lint
npm --prefix web run build
```

`scripts/verify_execution_mysql.py --suite all` 包含执行、变化面板与定时编排的真实 MySQL 验收。必须显式指定全新隔离库、独立本机端口和专用账号，禁止业务端口 3307；用法沿用脚本 `--help`，密码只通过 `/tmp` 内的私有文件提供。新增 `--suite scheduling` 可单独验证调度。

## 边界

- 名单适配器的失败、完整空名单、显式停用要分别表达；上游对快照新鲜度及有效授权负责，本模块不自行推断客户等级。
- 数据源没有变更游标时，自动补漏限于配置的历史回查范围；当前不支持从接口推断消息撤回。
- 原来同一分析版本已存在更晚事件时，从更早起点回放会安全停止，不能自行重置处理标记或覆盖历史。迁移启用前须选择与已有处理历史一致的起点，必要时明确使用独立版本。
- 切换模型、提示词或冻结策略后，原任务会停止并提示。不能借重启隐式触发全量重洗。
- 定时队列沿用单执行者及客户锁；更大客户量的吞吐、模型配额和完成延迟需要真实环境容量验收，未承诺所有客户均能在一个窗口内处理完。
